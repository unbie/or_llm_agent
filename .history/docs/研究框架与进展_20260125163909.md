# LLM驱动的元启发式算法求解VRP问题研究

> **项目名称**: OR-LLM-Agent + LLM-Heuristic  
> **研究方向**: 大语言模型自动生成元启发式算法算子  
> **当前阶段**: 原型验证 → 算法优化  
> **最后更新**: 2026年1月25日

---

## 一、研究概述

### 1.1 研究背景

传统运筹优化（OR）问题求解需要：
- 专业的数学建模知识
- 复杂的求解器配置经验
- 大量的手动调参工作

**核心问题**: 如何让LLM自动生成可执行的启发式算法代码，降低OR问题求解门槛？

### 1.2 研究目标

| 目标层级 | 具体内容 | 状态 |
|---------|---------|------|
| **基础目标** | LLM生成ALNS算子代码 | ✅ 已实现 |
| **进阶目标** | 生成的算子能有效优化解 | ✅ 已实现 |
| **高阶目标** | 达到或接近专业手工实现水平 | 🔄 进行中 |

### 1.3 核心创新点

1. **Prompt工程**: 设计结构化Prompt引导LLM生成正确的算子逻辑
2. **Skeleton框架**: 预定义求解器骨架，LLM只需填充核心算子
3. **自动纠错**: 多轮对话修复LLM生成代码的错误

## 三、算法设计

### 3.1 ALNS (Adaptive Large Neighborhood Search) 框架

#### 3.1.1 算法流程

```
1. 初始解生成 (贪心构造)
   │
2. 迭代优化循环 (max_iters次)
   │
   ├─► Destroy: 移除部分节点
   │    ├─ random_removal (随机移除)
   │    └─ worst_removal  (最差移除)
   │
   ├─► Insert: 重新插入节点  
   │    └─ greedy_insert   (贪心插入)
   │
   ├─► 接受准则 (模拟退火)
   │    └─ P(accept) = exp(-Δcost / T)
   │
   └─► 更新算子权重
        └─ 自适应学习有效算子
   │
3. 后处理 (可选的2-opt局部搜索)
   │
4. 输出最优解
```

#### 3.1.2 关键参数

| 参数 | 当前值 | 说明 |
|------|--------|------|
| `max_iters` | 150 | 单次运行迭代次数 |
| `num_runs` | 5 | 多次运行次数 |
| `base_seed` | 42 | 随机种子基数 |
| `T` (初始温度) | `cost * 0.01` | 模拟退火温度 |
| `alpha` (冷却率) | 0.995 | 缓慢冷却 |
| `rho` (学习率) | 0.1 | 算子权重更新速率 |

#### 3.1.3 移除比例策略

```python
# 根据无改善次数动态调整扰动幅度
if no_improve_count > 80:    # 长期停滞
    remove_ratio = 5% ~ 15%  # 大幅扰动
elif no_improve_count > 40:  # 中期停滞
    remove_ratio = 4% ~ 10%  # 中等扰动
else:                        # 正常优化
    remove_ratio = 2% ~ 6%   # 小步优化
```

### 3.2 LLM生成的算子

#### 3.2.1 random_removal

**功能**: 随机移除解中一定比例的客户节点

**关键实现点**:
- 支持比例(0-1)和数量(>1)两种ratio格式
- 使用 `min(n, len(all_nodes))` 防止越界
- 降序删除避免索引错位

#### 3.2.2 worst_removal

**功能**: 移除边际贡献最大的节点（即移除后成本减少最多）

**边际贡献公式**:
```
contrib = dist[prev][node] + dist[node][next] - dist[prev][next]
```

#### 3.2.3 greedy_insert ⭐（核心算子）

**功能**: 将移除的节点插回到成本增量最小的位置

**正确实现的关键**:

```python
for node in removed_nodes:
    # ✅ 检查点1: 必须初始化为无穷大
    best_cost = float('inf')  
    
    # ✅ 检查点2: 先搜索所有现有路径
    for route in solution:
        for pos in range(1, len(route)):
            cost_inc = calculate_insertion_cost(...)
            if cost_inc < best_cost:
                best_cost = cost_inc
                # 记录最佳位置
    
    # ✅ 检查点3: 搜索完成后才计算新建成本
    new_route_cost = dist[0][node] + dist[node][0]
    
    # ✅ 检查点4: 用 <= 比较，优先现有路径
    if best_cost <= new_route_cost:
        insert_to_existing_route()
    else:
        create_new_route()
```

**常见错误模式**:
```python
# ❌ 错误1: 初始化为新建成本
best_cost = dist[0][node] + dist[node][0]  # 导致永远新建路径

# ❌ 错误2: 用 < 比较
if best_cost < new_route_cost:  # 相等时也会新建路径

# ❌ 错误3: 边搜索边新建
for route in solution:
    new_route_cost = ...  # 过早计算
```

## 四、成本模型

### 4.1 总成本公式

$$
C_{total} = C_1 + C_2 + C_3
$$

其中：
- $C_1$: 配送成本
- $C_2$: 货损成本  
- $C_3$: 惩罚成本

### 4.2 配送成本 C1

$$
C_1 = \underbrace{m \cdot f}_{C_{11}:固定成本} + \underbrace{\sum_{k} c \cdot d_k}_{C_{12}:距离成本} + \underbrace{\sum_{k} c_t \cdot t_k}_{C_{13}:制冷成本}
$$

| 符号 | 含义 | 默认值 |
|------|------|--------|
| $m$ | 使用车辆数 | - |
| $f$ | 单车固定成本 | 240 |
| $c$ | 单位距离成本 | 3 |
| $c_t$ | 单位时间制冷成本 | 15 |
| $d_k$ | 第k条路径距离 | - |
| $t_k$ | 第k条路径时间 | - |

### 4.3 货损成本 C2

基于新鲜度衰减模型：

$$
C_2 = \sum_{i} p \cdot q_i \cdot \left(1 - e^{-\theta_1 t_{ik}} \cdot e^{-\theta_2 t'_{ik}}\right)
$$

| 符号 | 含义 | 默认值 |
|------|------|--------|
| $p$ | 商品单价 | 5000 |
| $\theta_1$ | 运输衰减系数 | 0.002 |
| $\theta_2$ | 服务衰减系数 | 0.005 |
| $t_{ik}$ | 到达客户i的时间 | - |
| $t'_{ik}$ | 累计服务时间 | - |

### 4.4 惩罚成本 C3

时间窗违反惩罚：

$$
C_3 = \sum_{i} \left( z_1 \cdot \max(0, E_i - a_i) + z_2 \cdot \max(0, a_i - L_i) \right)
$$

| 符号 | 含义 | 默认值 |
|------|------|--------|
| $z_1$ | 早到惩罚系数 | 20 |
| $z_2$ | 晚到惩罚系数 | 40 |
| $E_i$ | 最早服务时间 | - |
| $L_i$ | 最晚服务时间 | - |
| $a_i$ | 实际到达时间 | - |

## 五、研究进展

### 5.1 问题诊断与修复历程

#### 阶段1: 问题发现

**现象**: ALNS运行后"改善次数=0"，解质量无提升

**诊断方法**:
1. 添加 `_fallback_greedy_insert()` 备用算子
2. 对比LLM生成算子 vs 手写算子

**结论**: LLM生成的 `greedy_insert` 存在逻辑错误

#### 阶段2: 根因分析

**LLM典型错误**:
```python
# LLM生成的错误代码
new_route_cost = dist[0][node] + dist[node][0]
best_cost = new_route_cost  # ← 错误：应该是 float('inf')
```

**后果**: 每个节点都直接新建路径，路径数从23增加到100+

#### 阶段3: Prompt优化

**解决方案**: 在Prompt中添加结构化约束

```markdown
【greedy_insert】- 最关键的算子

**强制执行的代码结构**（必须严格按此顺序）：

# ===== 检查点1: 必须先初始化为无穷大 =====
best_cost = float('inf')

# ===== 检查点2: 先搜索所有现有路径 =====
for route in solution:
    ...

# ===== 检查点3: 搜索完成后才计算新建成本 =====
new_route_cost = dist[0][node] + dist[node][0]

# ===== 检查点4: 用 <= 比较，优先现有路径 =====
if best_cost <= new_route_cost:
```

#### 阶段4: 参数调优

| 参数 | 调整前 | 调整后 | 效果 |
|------|--------|--------|------|
| 初始温度 | `cost * 0.05` | `cost * 0.01` | 减少接受劣解 |
| 冷却率 | 0.99 | 0.995 | 延长搜索时间 |
| 移除比例 | 固定10-20% | 动态2-15% | 更精细的搜索 |

#### 阶段5: 稳定性增强

**问题**: 每次运行结果不同（元启发式的随机性）

**解决方案**:
1. 添加 `seed` 参数实现可重复性
2. 实现 `solve_multi_run()` 多次运行取最优

```python
# 多次运行策略
best_sol, best_cost = solver.solve_multi_run(
    max_iters=150,   # 每次150次迭代
    num_runs=5,      # 运行5次
    base_seed=42     # 种子42,43,44,45,46
)
```
