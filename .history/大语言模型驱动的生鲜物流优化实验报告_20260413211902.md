## 1. 研究目标与问题定义

本文档用于毕业论文中的方法与实验章节，目标是把本项目中“让 LLM 在已有 ALNS 算子基础上迭代优化五次”的全过程写清楚，覆盖以下内容：

* 系统输入输出与代码模块分工
* 每轮优化的提示词构造、代码生成、验证、回退与接受机制
* 五个算子（3 破坏 + 2 修复）的可优化思路
* 轮次记录方式、目录结构与结果文件
* 实验结果汇总与可复现步骤

研究对象是带时间窗与冷链成本约束的 VRP 问题，综合成本目标为

$$
Z = C_{11} + C_{12} + C_{13} + C_2 + C_3
$$

其中：

* $C_{11}$ 是车辆固定成本（车辆数 × 240）
* $C_{12}$ 是距离成本（总距离 × 3）
* $C_{13}$ 是制冷成本（总时长 × 15）
* $C_2$ 是货损成本（与服务时序相关）
* $C_3$ 是时间窗惩罚成本（早到/迟到）

核心结论先行：本项目不是“最短路径”问题，而是“多成本耦合最小化”问题，节点插入顺序直接影响 $C_2$ 和 $C_3$，因此算子改进必须基于完整成本计算。

## 2. 代码架构与职责分工

### 2.1 关键脚本与作用

* run_baseline_alns.py
	* 作用：运行纯手工 ALNS 基线实验，输出标准化结果 JSON
	* 特点：支持单例测试与全量批量实验，便于与 LLM 版本对比
* run_llm_optimize.py
	* 作用：执行“Round 0 基线 + Round 1..N LLM 迭代 + Final 验证”完整流程
	* 特点：每轮保留代码、LLM 分析、完整回复、结果 JSON
* optimize_prompts.py
	* 作用：定义结构化 Prompt 模板，约束 LLM 在固定方法签名内做逻辑优化
	* 特点：内置数据集特征说明、成本模型说明、历史失败规避机制

### 2.2 算子接口约束

LLM 被严格限制只改 5 个方法体，不允许改构造函数或新增公共方法：

* 破坏算子
	* _random_removal(self, solution, ratio)
	* _route_removal(self, solution, ratio)
	* _string_removal(self, solution, ratio)
* 修复算子
	* _greedy_insert(self, solution, removed_nodes)
	* _regret_insert(self, solution, removed_nodes)

并要求修复阶段必须调用完整成本接口 calculate_route_cost()，避免退化成仅看距离增量的简化近似。

## 3. 端到端实验流程

### 3.1 基线阶段（Round 0）

流程从手工基线算子开始运行，得到 baseline_cost、路径数、耗时、收敛轨迹、算子调用统计、成本分解占比等指标。该结果写入 round_0_baseline/result.json。

此步骤的作用是提供“可比较、可回退”的锚点。

### 3.2 每轮 LLM 优化阶段（Round 1 到 Round 5）

每一轮包含 7 个固定步骤：

1. 构建 Prompt
	 * 拼接当前代码
	 * 拼接性能报告（改善率、停滞迭代、成本分解、算子统计）
	 * 拼接历史记录（上一轮是否退步、退步幅度、修改摘要）
2. 调用 LLM 生成修改方案
3. 从回复中提取 Python 代码块
4. 验证代码完整性与语法
	 * 若失败，最多重试 3 次
5. 执行新算子并评估新成本
6. 与上一版 best_cost 比较
	 * 若 new_cost < prev_cost，标记 accepted，更新 current_code
	 * 否则标记 rejected，保留上一版 current_code
7. 落盘保存
	 * round_k_accepted 或 round_k_rejected
	 * 保存 code.py、llm_analysis.md、llm_full_response.md、result.json

这套机制保证了“可以大胆探索，但不会污染当前最优版本”。

### 3.3 最终验证阶段（Final）

五轮结束后，系统会使用“历史最优代码 best_ever_code”做更高迭代数的最终验证（默认 final_iters=1000），并输出 final_best/result.json。

该步骤用于减少单轮随机性影响，给出可汇报的最终结果。

## 4. 五轮优化机制写法（论文可直接引用）

本项目采用“固定轮次数 + 逐轮可回退”的策略。一次标准实验可表述为：

* Round 0：基线运行，建立参照成本
* Round 1：LLM 第一次针对性修改
* Round 2：基于 Round 1 结果继续修改
* Round 3：继续迭代，并带入历史失败记录
* Round 4：继续迭代，重点突破停滞区间
* Round 5：最后一次 LLM 迭代
* Final：调用历史最优代码做最终验证

在实现上，max_rounds 默认等于 5，正好对应论文中“五轮优化”的实验设计。

## 5. 五个算子的详细优化思路

### 5.1 _random_removal 的优化方向

原始随机移除覆盖面广，但目的性弱。LLM 优化重点通常包括：

* 提高样本多样性，避免集中删除同一路径局部节点
* 在随机中引入轻度偏置，例如优先抽取高惩罚贡献节点
* 控制 ratio 与最小移除数，避免破坏过弱或过强

### 5.2 _route_removal 的优化方向

路径级破坏可以快速重组解结构，适合聚类数据。可优化点包括：

* 按路径代价密度而非纯随机移除
* 引入目标客户数上限，防止一次移除过量
* 在 C1/C2 数据上引入“同簇重构”意识

### 5.3 _string_removal 的优化方向

连续片段移除有利于打破局部结构。可优化点包括：

* 动态片段长度（根据停滞程度调整）
* 在时间窗冲突路段优先切片
* 与 route_removal 互补，形成“局部 + 全局”双尺度破坏

### 5.4 _greedy_insert 的优化方向

贪心插入是恢复阶段主力。关键改进思路：

* 坚持完整成本增量评估，不只看距离
* 引入候选位置列表，减少全量遍历开销
* 对新开路径成本设置合理门槛，避免过度增车

### 5.5 _regret_insert 的优化方向

后悔插入负责“先放最难放的点”。常见升级方向：

* 从 Regret-2 扩展到 Regret-k
* 将时间窗风险纳入后悔值
* 在并列候选中引入轻量随机扰动，提升逃逸能力

## 6. Prompt 工程与历史记忆机制

optimize_prompts.py 的设计不是让 LLM 重写求解器，而是让它做受约束的局部代码演进。Prompt 的信息组织顺序如下：

* 成本模型与 API 可用能力
* 当前算子代码
* 当前轮性能画像
* 高级策略建议（最差移除、Regret-k、候选列表等）
* 历史记录与“禁止重复失败思路”提示

历史记录段会写入“第几轮、成本变化、升降幅、修改摘要”，用于抑制重复无效优化。

## 7. 结果记录格式与目录规范

单个实例目录结构如下：

* round_0_baseline/
* round_1_accepted 或 round_1_rejected
* round_2_accepted 或 round_2_rejected
* ...
* round_5_accepted 或 round_5_rejected
* final_best/
* summary.json

每轮 result.json 至少记录：

* round
* type（baseline/accepted/rejected/skipped/failed/final）
* cost 或 best_cost
* prev_cost 与 change_pct（迭代轮）
* num_routes
* elapsed_time

这确保论文中的每一行结论都可回溯到具体文件。

## 8. 结果汇总与解释

### 8.1 Baseline 与 LLM 最优结果对比

基于自动汇总表 instance_baseline_vs_llm_best.csv，四个实例的结果如下。

| 实例 | Baseline 成本 | LLM 最优成本 | 降本额（Baseline-LLM） | 降本率 |
| --- | ---: | ---: | ---: | ---: |
| c1_c101 | 44589.994556 | 43597.542459 | 992.452096 | 2.225728% |
| c1_c105 | 43258.101135 | 41956.554046 | 1301.547089 | 3.008794% |
| c2_c201 | 96840.923180 | 96636.059836 | 204.863344 | 0.211546% |
| c2_c205 | 92947.043053 | 93038.533114 | -91.490061 | -0.098432% |

### 8.2 现象解读

* C1 类实例改进更明显，说明在聚类且时间窗紧张条件下，算子重构空间更大。
* C2 类实例改进较小，说明基线已较强，LLM 的边际收益受限。
* 单个负改进样本（c2_c205）说明策略仍存在数据依赖性，需要在 Prompt 中加强“宽时间窗场景”的专门约束。

## 10. 结论与后续工作

本文给出了从代码到结果的完整技术链路。方法上，LLM 并非替代 ALNS，而是作为“算子改进器”嵌入闭环。工程上，五轮迭代、可回退接受机制、历史失败记忆和最终复验共同保证了稳定性与可复现性。结果上，四个实例中有三个实现降本，最佳降幅达到 3.008794%。

后续可继续沿三条线扩展：

* 在 Prompt 中增加按数据集类型的专用约束模板
* 引入多种子重复实验并报告置信区间
* 把 accepted/rejected 轮次特征做成元学习数据集，训练自动算子推荐器
