## 1. 项目概述

### 1.1 研究背景

车辆路径问题（Vehicle Routing Problem, VRP）是运筹优化领域的经典 NP-hard 问题。在生鲜物流场景下，除了传统的容量约束和时间窗约束外，还需要考虑产品新鲜度衰减、冷链制冷成本、时间窗违反惩罚等多维目标，问题复杂度显著提升。

自适应大邻域搜索（Adaptive Large Neighborhood Search, ALNS）是求解此类问题的主流元启发式方法。传统的 ALNS 实现依赖人工设计破坏（Destroy）和修复（Repair）算子，开发周期长、可移植性差。

### 1.2 研究目标

本项目基于 OR-LLM-Agent 框架，探索利用推理型大语言模型（DeepSeek R1）**自动生成** ALNS 算法中的启发式算子代码，实现"LLM 生成算子 + 框架执行求解"的混合架构。具体目标包括：

- 设计 ALNS 算法框架（Skeleton），提供标准化的求解流程
- 通过提示工程（Prompt Engineering）引导 LLM 生成 5 个启发式算子
- 构建自动执行管线，实现从代码生成到结果可视化的全流程自动化
- 在 Solomon 基准上验证算法性能

### 1.3 核心创新

1. **插件式架构**: 将 ALNS 框架与算子实现解耦，LLM 生成的代码作为"插件"注入框架
2. **自动调试机制**: 多轮对话反馈执行错误，LLM 自主修正代码直至成功运行
3. **完整成本模型**: 融合固定成本、距离成本、制冷成本、货损成本和时间窗惩罚的五维成本函数
4. **自适应权重管理**: 引入权重下限保护机制，防止算子饥饿（Operator Starvation）

## 4. 算法设计

### 4.1 ALNS 算法框架

自适应大邻域搜索（ALNS）由 Ropke & Pisinger (2006) 提出，是大邻域搜索（LNS）的扩展，核心思想是在多个破坏-修复算子之间进行自适应选择。

#### 算法伪代码

```
Algorithm: ALNS for VRP
───────────────────────────────────────────
Input:  问题数据 D, 最大迭代次数 N
Output: 最优解 s*, 最优成本 c*

1:  s ← GenerateInitialSolution(D)        // 3 种策略取最优
2:  s* ← s; c* ← Cost(s)
3:  T ← 0.10 × c*                         // SA 初始温度
4:  α ← 0.02^(1/N)                        // 冷却系数
5:  w_d ← [1.0, 1.0, 1.0]                // 破坏算子权重
6:  w_i ← [1.0, 1.0]                     // 修复算子权重
7:
8:  for iter = 1 to N do
9:      d ← RouletteSelect(destroy_ops, w_d)   // 轮盘赌选择
10:     r ← RouletteSelect(insert_ops, w_i)
11:     ratio ← AdaptiveRatio(no_improve)       // 自适应破坏比例
12:     (partial, removed) ← d(s, ratio)
13:     s' ← r(partial, removed)
14:
15:     if Validate(s') then
16:         Δ ← Cost(s') − Cost(s)
17:         if Δ < 0 then                       // 改进
18:             s ← s'
19:             if Cost(s') < c* then            // 全局最优
20:                 s* ← s'; c* ← Cost(s')
21:                 UpdateWeights(σ₁=33)
22:             else
23:                 UpdateWeights(σ₂=9)
24:         elif rand() < exp(−Δ/T) then        // SA 接受
25:             s ← s'
26:             UpdateWeights(σ₃=3)
27:         else
28:             UpdateWeights(σ₄=0)              // 拒绝
29:
30:     T ← T × α
31:     if no_improve > threshold then
32:         s ← s*; T ← Reheat()               // 重启 + 再加热
33:
34: s* ← LocalSearch_2opt(s*)                   // 后处理
35: return s*, c*
```

### 4.2 算子设计

本系统包含 **3 个破坏算子** 和 **2 个修复算子**，均由 LLM 自动生成：

| 类型 | 算子名称 | 策略描述 | 复杂度 |
|------|----------|----------|--------|
| 破坏 | `random_removal` | 随机选择 $k$ 个客户节点移除 | $O(n)$ |
| 破坏 | `route_removal` | 随机选择整条路径移除 | $O(K)$ |
| 破坏 | `string_removal` | 移除路径中连续的节点段 | $O(n)$ |
| 修复 | `greedy_insert` | 逐个将节点插入成本增量最小的位置 | $O(n^2 K)$ |
| 修复 | `regret_insert` | 优先插入"后悔值"最大的节点（最佳与次佳位置差） | $O(n^2 K)$ |

其中 $n$ 为客户数量，$K$ 为路径数量。

### 4.3 关键参数配置

| 参数 | 符号 | 取值 | 说明 |
|------|------|------|------|
| 最大迭代次数 | $N$ | 1000 | 平衡计算时间与解质量 |
| 初始温度 | $T_0$ | $0.10 \times c_0$ | SA 初始接受范围约 10% |
| 冷却系数 | $\alpha$ | $0.02^{1/N}$ | 线性冷却策略 |
| 记忆系数 | $\rho$ | 0.1 | 权重更新平滑因子 |
| 奖励分数 | $\sigma_1, \sigma_2, \sigma_3, \sigma_4$ | 33, 9, 3, 0 | 四档分数体系 |
| 权重下限 | $w_{min}$ | 0.1 | 防止算子饥饿 |
| 重启阈值 | — | $0.6N$ | 无改善超过 60% 迭代则重启 |
| 初始解数量 | — | 3 | 需求排序 / 时间窗紧迫度 / 随机 |

### 4.4 自适应破坏比例

破坏比例根据无改善计数器动态调整：

$$
\text{ratio} =
\begin{cases}
12\%\text{-}18\% & \text{if } \text{no\_improve} \leq 0.27N \\
15\%\text{-}20\% & \text{if } 0.27N < \text{no\_improve} \leq 0.53N \\
20\%\text{-}30\% & \text{if } \text{no\_improve} > 0.53N
\end{cases}
$$

### 4.5 权重更新机制

算子权重按照以下公式更新：

$$
w_i^{(t+1)} = (1 - \rho) \cdot w_i^{(t)} + \rho \cdot \sigma
$$

其中 $\sigma$ 为当次迭代的奖励分数。更新后执行下限保护：

$$
w_i^{(t+1)} = \max\left(w_i^{(t+1)},\ w_{min}\right)
$$

每隔 $\lfloor 0.25N \rfloor$ 次迭代，对所有权重进行归一化：

$$
w_i \leftarrow \frac{w_i}{\sum_j w_j} \times |\mathcal{O}|
$$

### 4.6 备用机制（Fallback）

为保证系统鲁棒性，框架层为每个算子提供备用实现。当 LLM 生成的算子运行时抛出异常时，自动切换到对应的备用算子：

- 破坏备用: `_fallback_random_removal`, `_fallback_worst_removal`, `_fallback_related_removal`, `_fallback_shaw_removal`, `_fallback_history_removal`, `_fallback_cluster_removal`
- 修复备用: `_fallback_greedy_insert`, `_fallback_regret_insert`, `_fallback_random_insert`

## 5. 成本模型

### 5.1 总成本函数

生鲜物流 VRP 的总成本由五个分项组成：

$$
C_{total} = C_{11} + C_{12} + C_{13} + C_2 + C_3
$$

### 5.2 各分项详述

**C₁₁ — 车辆固定成本**

$$
C_{11} = K \times f, \quad f = 240\ \text{元/车}
$$

其中 $K$ 为使用的车辆数量（路径条数）。

**C₁₂ — 运输距离成本**

$$
C_{12} = \sum_{k=1}^{K} \left( \sum_{(i,j) \in \text{route}_k} d_{ij} \right) \times c, \quad c = 3\ \text{元/km}
$$

**C₁₃ — 冷链制冷成本**

$$
C_{13} = \sum_{k=1}^{K} T_k^{drive} \times c_t, \quad c_t = 15\ \text{元/h}
$$

其中 $T_k^{drive}$ 为路径 $k$ 的总行驶时间（不含服务时间）。

**C₂ — 货损成本（新鲜度衰减模型）**

$$
C_2 = \sum_{k=1}^{K} \sum_{i \in \text{route}_k} p \cdot D_i \cdot \max(r_i - \delta_1, 0)
$$

其中新鲜度衰减率 $r_i$ 基于指数衰减模型：

$$
r_i = 1 - \exp\left(-\theta_1 (t_{ik} - t'_{ik}) - \theta_2 \cdot t'_{ik}\right)
$$

| 参数 | 取值 | 含义 |
|------|------|------|
| $p$ | 5000 元/吨 | 产品单价 |
| $\theta_1$ | 0.002 | 运输损耗系数 |
| $\theta_2$ | 0.005 | 装卸损耗系数 |
| $\delta_1$ | 0.02 | 允许损耗阈值 |

**C₃ — 时间窗惩罚成本**

采用分段线性惩罚函数：

$$
f_i(t) =
\begin{cases}
z_1 \cdot \dfrac{e_i - t}{e_i - E_i} & \text{if } E_i \leq t < e_i\ (\text{软早到}) \\[8pt]
0 & \text{if } e_i \leq t \leq l_i\ (\text{正常}) \\[8pt]
z_2 \cdot \dfrac{t - l_i}{L_i - l_i} & \text{if } l_i < t \leq L_i\ (\text{软迟到}) \\[8pt]
300 & \text{if } t < E_i \text{ or } t > L_i\ (\text{硬违反})
\end{cases}
$$

| 参数 | 取值 | 含义 |
|------|------|------|
| $z_1$ | 20 元/h | 早到惩罚系数 |
| $z_2$ | 40 元/h | 迟到惩罚系数 |
| $[e_i, l_i]$ | — | 软时间窗（客户偏好） |
| $[E_i, L_i]$ | — | 硬时间窗（绝对约束） |

### 6.2 关键设计决策

1. **正面引导**: 仅列出需要实现的 5 个算子名称，避免提及"不需要实现的算子"（如 `worst_removal`），防止 LLM 反向注意
2. **成本计算强制**: 在模板最开头、算子说明中、检查清单中三次强调必须使用 `calculate_route_cost()`
3. **完整示例**: 提供 `random_removal` 的完整代码实现作为参考模板，其余算子提供关键代码片段
4. **统一 `__init__`**: 提示模板中不要求 LLM 生成 `__init__`，由框架层统一注入，消除属性不匹配风险

### 6.3 代码重构机制

在 `generate_or_code_solver()` 中，对 LLM 生成的代码执行以下处理：

1. **`__init__` 替换**: 无论 LLM 是否生成了 `__init__`，一律替换为框架统一的版本
2. **缺失方法补全**: 自动检测 5 个必需方法，缺失的自动添加桩代码（Stub）
3. **代码合并**: `Skeleton + Plugin + 执行代码` 拼接为完整可执行脚本
4. **结构验证**: 检查最终代码中 `HeuristicSolver` 和 `HeuristicPlugin` 各出现恰好 1 次

代码通过 `subprocess.Popen` 在独立子进程中执行，主要特性：

- **流式输出**: 使用 `-u` 标志禁用 Python 输出缓冲，实时读取 `stdout`

### 8.1 优化时间线


### 8.2 关键问题与解决方案

#### 问题 1: 多次运行冗余

**分析**: 单次 `solve()` 已内置三重随机化机制——(1) 3 个初始解策略，(2) 模拟退火随机接受，(3) 重启 + 再加热。因此多次 `solve_multi_run(num_runs=3)` 的边际收益极低。

**解决**: 将调用从 `solver.solve_multi_run(max_iters=800, num_runs=3)` 简化为 `solver.solve(max_iters=1000)`，同时将节省的算力分配给更多迭代次数（800→1000）。

#### 问题 2: 算子饥饿（Operator Starvation）

**现象**: 第一次运行结果显示 `route_removal` 仅被使用约 32 次（占 3.2%），而 `random_removal` 高达约 500 次（约 50%）。权重更新后 `route_removal` 的权重趋近于零，几乎不再被选中。

**分析**: ALNS 权重更新公式 $w \leftarrow (1-\rho) \cdot w + \rho \cdot \sigma$ 在连续获得 $\sigma=0$ 时导致权重指数衰减，最终趋近于零。

**解决**: 引入权重下限保护：
```python
min_weight = 0.1
self.d_weights = [max(w, min_weight) for w in self.d_weights]
```
**效果**: `route_removal` 使用量翻倍至约 60 次，搜索多样性提升。

#### 问题 3: 图表标注重叠

**现象**: 算子性能图 (c) 中，使用次数低的算子（如 `route_removal`）的柱子很矮，柱顶数值标注与成功率折线标注在视觉上重叠。

**解决**: 双维度动态定位：
1. **柱顶标注**: 低于最大值 15% 的柱子，标注使用加粗字体并向上偏移
2. **成功率标注**: 计算标注点与柱顶的归一化距离，距离过近时翻转标注方向（上方→下方）

#### 问题 4: Notebook 代码重复

**现象**: `test.ipynb` 中内联了 858 行代码，是 `llm_heuristic.py` 的完整拷贝，维护时需要同步修改两处。

**解决**: 重构 Notebook 为 ~85 行的 import 方式：
```python
from llm_heuristic import generate_or_code_solver, visualize_results, ...
```

### 9.3 优化对比

| 版本 | 迭代 | 运行方式 | 最优成本 | 改进幅度 |
|------|------|----------|----------|----------|
| V1 (初始) | 800 | 3次运行 | 42,775.07 | — |
| V2 (优化后) | 1000 | 单次运行 | **42,023.80** | **−751.27 (−1.8%)** |

### 9.4 算子统计分析

最终运行的算子使用情况：

| 算子 | 类型 | 使用次数 | 成功次数 | 成功率 |
|------|------|----------|----------|--------|
| `random_removal` | 破坏 | ~632 | ~304 | 48.1% |
| `route_removal` | 破坏 | ~60 | ~5 | ~8.3% |
| `string_removal` | 破坏 | ~317 | ~86 | 27.1% |
| `greedy_insert` | 修复 | ~237 | ~73 | 30.8% |
| `regret_insert` | 修复 | ~763 | ~322 | 42.2% |

**分析**:

1. **`random_removal` 主导破坏**: 约 63% 的破坏操作由随机移除完成，成功率最高（48.1%），说明在此问题规模下随机扰动的探索效率很高
2. **`regret_insert` 优于 `greedy_insert`**: 后悔插入的使用量（~763 次）远高于贪心插入（~237 次），且成功率更高（42.2% vs 30.8%），符合文献中后悔插入在时间窗约束问题中的优势
3. **`route_removal` 使用量低但有价值**: 虽然仅约 60 次使用，但权重下限保护机制确保了搜索多样性，避免陷入单一搜索模式
4. **收敛持续至 ~900 轮**: 从 800 次扩展到 1000 次迭代后，算法在约 900 轮仍找到了改进，证明了增加迭代预算的价值

### 9.5 收敛行为

从收敛曲线 (a) 可以观察到：

- **快速下降期** (0-200 轮): 初始解快速改进，成本大幅下降
- **波动探索期** (200-600 轮): SA 温度较高，当前成本呈现显著波动（灰色曲线），但最优成本稳步下降
- **精细优化期** (600-900 轮): 温度降低，波动减小，间歇性发现更优解
- **收敛稳定期** (900-1000 轮): 算法基本收敛，成本趋于稳定

这一行为模式体现了 SA 接受准则在探索（Exploration）与利用（Exploitation）之间的平衡。

## 10. 结论与展望

### 10.1 主要结论

1. **LLM 可有效生成 ALNS 算子**: DeepSeek R1 在提示工程引导下，能够生成功能正确的破坏和修复算子代码，在 Solomon C105 基准上取得 42,023.80 的目标函数值
2. **插件式架构保证鲁棒性**: Skeleton + Plugin 的解耦设计，配合 Fallback 机制，即使 LLM 生成的部分算子存在缺陷，系统仍能正常运行
3. **自适应机制的重要性**: 权重下限保护、自适应破坏比例、重启再加热等机制显著影响算法性能，防止过早收敛和算子饥饿
4. **单次运行即可**: 内置的三重随机化机制使单次 `solve()` 已具备足够的搜索能力，多次运行的边际收益极低

### 10.2 局限性

1. **问题规模**: 当前仅在 100 客户规模上测试，更大规模实例（500+客户）的性能有待验证
2. **LLM 依赖**: 算子质量取决于 LLM 的代码生成能力，不同 LLM 可能产生差异较大的结果
3. **成本函数固定**: 当前成本模型为硬编码，扩展到其他 VRP 变体（如多仓库、异构车队）需要重新设计
4. **缺少对比基线**: 未与传统手工实现的 ALNS 或其他元启发式算法进行系统对比

### 10.3 未来工作

1. **多 LLM 对比**: 在相同提示下对比 GPT-4o、Claude、Gemini 等模型生成算子的质量
2. **自适应提示**: 根据首轮执行结果自动调整提示词，形成"提示-执行-反馈"闭环
3. **大规模测试**: 在 Solomon R 类和 RC 类实例，以及 Gehring & Homberger 大规模实例上验证
4. **算子进化**: 多轮对话中让 LLM 根据算子统计数据改进低效算子的实现
