## 1. 项目概述

### 1.1 研究背景

车辆路径问题（Vehicle Routing Problem, VRP）是运筹优化领域的经典 NP-hard 问题。在生鲜物流场景下，除了传统的容量约束和时间窗约束外，还需要考虑产品新鲜度衰减、冷链制冷成本、时间窗违反惩罚等多维目标，问题复杂度显著提升。

自适应大邻域搜索（Adaptive Large Neighborhood Search, ALNS）是求解此类问题的主流元启发式方法。传统的 ALNS 实现依赖人工设计破坏（Destroy）和修复（Repair）算子，开发周期长、可移植性差。

### 1.2 研究目标

本项目基于 OR-LLM-Agent 框架，探索利用推理型大语言模型（DeepSeek R1）**自动生成** ALNS 算法中的启发式算子代码，实现"LLM 生成算子 + 框架执行求解"的混合架构。具体目标包括：

- 设计 ALNS 算法框架（Skeleton），提供标准化的求解流程
- 通过提示工程（Prompt Engineering）引导 LLM 生成 5 个启发式算子
- 构建自动执行管线，实现从代码生成到结果可视化的全流程自动化
- 在 Solomon 基准上验证算法性能

### 1.3 核心创新

1. **插件式架构**: 将 ALNS 框架与算子实现解耦，LLM 生成的代码作为"插件"注入框架
2. **自动调试机制**: 多轮对话反馈执行错误，LLM 自主修正代码直至成功运行
3. **完整成本模型**: 融合固定成本、距离成本、制冷成本、货损成本和时间窗惩罚的五维成本函数
4. **自适应权重管理**: 引入权重下限保护机制，防止算子饥饿（Operator Starvation）

## 4. 算法设计

### 4.1 ALNS 算法框架

自适应大邻域搜索（ALNS）由 Ropke & Pisinger (2006) 提出，是大邻域搜索（LNS）的扩展，核心思想是在多个破坏-修复算子之间进行自适应选择。

#### 算法伪代码

```
Algorithm: ALNS for VRP
───────────────────────────────────────────
Input:  问题数据 D, 最大迭代次数 N
Output: 最优解 s*, 最优成本 c*

1:  s ← GenerateInitialSolution(D)        // 3 种策略取最优
2:  s* ← s; c* ← Cost(s)
3:  T ← 0.10 × c*                         // SA 初始温度
4:  α ← 0.02^(1/N)                        // 冷却系数
5:  w_d ← [1.0, 1.0, 1.0]                // 破坏算子权重
6:  w_i ← [1.0, 1.0]                     // 修复算子权重
7:
8:  for iter = 1 to N do
9:      d ← RouletteSelect(destroy_ops, w_d)   // 轮盘赌选择
10:     r ← RouletteSelect(insert_ops, w_i)
11:     ratio ← AdaptiveRatio(no_improve)       // 自适应破坏比例
12:     (partial, removed) ← d(s, ratio)
13:     s' ← r(partial, removed)
14:
15:     if Validate(s') then
16:         Δ ← Cost(s') − Cost(s)
17:         if Δ < 0 then                       // 改进
18:             s ← s'
19:             if Cost(s') < c* then            // 全局最优
20:                 s* ← s'; c* ← Cost(s')
21:                 UpdateWeights(σ₁=33)
22:             else
23:                 UpdateWeights(σ₂=9)
24:         elif rand() < exp(−Δ/T) then        // SA 接受
25:             s ← s'
26:             UpdateWeights(σ₃=3)
27:         else
28:             UpdateWeights(σ₄=0)              // 拒绝
29:
30:     T ← T × α
31:     if no_improve > threshold then
32:         s ← s*; T ← Reheat()               // 重启 + 再加热
33:
34: s* ← LocalSearch_2opt(s*)                   // 后处理
35: return s*, c*
```

### 4.2 算子设计

本系统包含 **3 个破坏算子** 和 **2 个修复算子**，均由 LLM 自动生成：

| 类型 | 算子名称         | 策略描述                                       | 复杂度     |
| ---- | ---------------- | ---------------------------------------------- | ---------- |
| 破坏 | `random_removal` | 随机选择 $k$ 个客户节点移除                    | $O(n)$     |
| 破坏 | `route_removal`  | 随机选择整条路径移除                           | $O(K)$     |
| 破坏 | `string_removal` | 移除路径中连续的节点段                         | $O(n)$     |
| 修复 | `greedy_insert`  | 逐个将节点插入成本增量最小的位置               | $O(n^2 K)$ |
| 修复 | `regret_insert`  | 优先插入"后悔值"最大的节点（最佳与次佳位置差） | $O(n^2 K)$ |

其中 $n$ 为客户数量，$K$ 为路径数量。

### 4.3 关键参数配置

| 参数         | 符号                                     | 取值              | 说明                           |
| ------------ | ---------------------------------------- | ----------------- | ------------------------------ |
| 最大迭代次数 | $N$                                      | 1000              | 平衡计算时间与解质量           |
| 初始温度     | $T_0$                                    | $0.10 \times c_0$ | SA 初始接受范围约 10%          |
| 冷却系数     | $\alpha$                                 | $0.02^{1/N}$      | 线性冷却策略                   |
| 记忆系数     | $\rho$                                   | 0.1               | 权重更新平滑因子               |
| 奖励分数     | $\sigma_1, \sigma_2, \sigma_3, \sigma_4$ | 33, 9, 3, 0       | 四档分数体系                   |
| 权重下限     | $w_{min}$                                | 0.1               | 防止算子饥饿                   |
| 重启阈值     | —                                        | $0.6N$            | 无改善超过 60% 迭代则重启      |
| 初始解数量   | —                                        | 3                 | 需求排序 / 时间窗紧迫度 / 随机 |

### 4.4 自适应破坏比例

破坏比例根据无改善计数器动态调整：

$$
\text{ratio} =
\begin{cases}
12\%\text{-}18\% & \text{if } \text{no\_improve} \leq 0.27N \\
15\%\text{-}20\% & \text{if } 0.27N < \text{no\_improve} \leq 0.53N \\
20\%\text{-}30\% & \text{if } \text{no\_improve} > 0.53N
\end{cases}
$$

### 4.5 权重更新机制

算子权重按照以下公式更新：

$$
w_i^{(t+1)} = (1 - \rho) \cdot w_i^{(t)} + \rho \cdot \sigma
$$

其中 $\sigma$ 为当次迭代的奖励分数。更新后执行下限保护：

$$
w_i^{(t+1)} = \max\left(w_i^{(t+1)},\ w_{min}\right)
$$

每隔 $\lfloor 0.25N \rfloor$ 次迭代，对所有权重进行归一化：

$$
w_i \leftarrow \frac{w_i}{\sum_j w_j} \times |\mathcal{O}|
$$

### 4.6 备用机制（Fallback）

为保证系统鲁棒性，框架层为每个算子提供备用实现。当 LLM 生成的算子运行时抛出异常时，自动切换到对应的备用算子：

- 破坏备用: `_fallback_random_removal`, `_fallback_worst_removal`, `_fallback_related_removal`, `_fallback_shaw_removal`, `_fallback_history_removal`, `_fallback_cluster_removal`
- 修复备用: `_fallback_greedy_insert`, `_fallback_regret_insert`, `_fallback_random_insert`

## 5. 成本模型

### 5.1 总成本函数

生鲜物流 VRP 的总成本由五个分项组成：

$$
C_{total} = C_{11} + C_{12} + C_{13} + C_2 + C_3
$$

### 5.2 各分项详述

**C₁₁ — 车辆固定成本**

$$
C_{11} = K \times f, \quad f = 240\ \text{元/车}
$$

其中 $K$ 为使用的车辆数量（路径条数）。

**C₁₂ — 运输距离成本**

$$
C_{12} = \sum_{k=1}^{K} \left( \sum_{(i,j) \in \text{route}_k} d_{ij} \right) \times c, \quad c = 3\ \text{元/km}
$$

**C₁₃ — 冷链制冷成本**

$$
C_{13} = \sum_{k=1}^{K} T_k^{drive} \times c_t, \quad c_t = 15\ \text{元/h}
$$

其中 $T_k^{drive}$ 为路径 $k$ 的总行驶时间（不含服务时间）。

**C₂ — 货损成本（新鲜度衰减模型）**

$$
C_2 = \sum_{k=1}^{K} \sum_{i \in \text{route}_k} p \cdot D_i \cdot \max(r_i - \delta_1, 0)
$$

其中新鲜度衰减率 $r_i$ 基于指数衰减模型：

$$
r_i = 1 - \exp\left(-\theta_1 (t_{ik} - t'_{ik}) - \theta_2 \cdot t'_{ik}\right)
$$

| 参数       | 取值       | 含义         |
| ---------- | ---------- | ------------ |
| $p$        | 5000 元/吨 | 产品单价     |
| $\theta_1$ | 0.002      | 运输损耗系数 |
| $\theta_2$ | 0.005      | 装卸损耗系数 |
| $\delta_1$ | 0.02       | 允许损耗阈值 |

**C₃ — 时间窗惩罚成本**

采用分段线性惩罚函数：

$$
f_i(t) =
\begin{cases}
z_1 \cdot \dfrac{e_i - t}{e_i - E_i} & \text{if } E_i \leq t < e_i\ (\text{软早到}) \\[8pt]
0 & \text{if } e_i \leq t \leq l_i\ (\text{正常}) \\[8pt]
z_2 \cdot \dfrac{t - l_i}{L_i - l_i} & \text{if } l_i < t \leq L_i\ (\text{软迟到}) \\[8pt]
300 & \text{if } t < E_i \text{ or } t > L_i\ (\text{硬违反})
\end{cases}
$$

| 参数         | 取值    | 含义                 |
| ------------ | ------- | -------------------- |
| $z_1$        | 20 元/h | 早到惩罚系数         |
| $z_2$        | 40 元/h | 迟到惩罚系数         |
| $[e_i, l_i]$ | —       | 软时间窗（客户偏好） |
| $[E_i, L_i]$ | —       | 硬时间窗（绝对约束） |

### 6.2 关键设计决策

1. **正面引导**: 仅列出需要实现的 5 个算子名称，避免提及"不需要实现的算子"（如 `worst_removal`），防止 LLM 反向注意
2. **成本计算强制**: 在模板最开头、算子说明中、检查清单中三次强调必须使用 `calculate_route_cost()`
3. **完整示例**: 提供 `random_removal` 的完整代码实现作为参考模板，其余算子提供关键代码片段
4. **统一 `__init__`**: 提示模板中不要求 LLM 生成 `__init__`，由框架层统一注入，消除属性不匹配风险

### 6.3 代码重构机制

在 `generate_or_code_solver()` 中，对 LLM 生成的代码执行以下处理：

1. **`__init__` 替换**: 无论 LLM 是否生成了 `__init__`，一律替换为框架统一的版本
2. **缺失方法补全**: 自动检测 5 个必需方法，缺失的自动添加桩代码（Stub）
3. **代码合并**: `Skeleton + Plugin + 执行代码` 拼接为完整可执行脚本
4. **结构验证**: 检查最终代码中 `HeuristicSolver` 和 `HeuristicPlugin` 各出现恰好 1 次

### 8.3 A 类问题: LLM 代码生成相关

#### P1: `__init__` 属性不匹配 (AttributeError)

**现象**: LLM 生成的 `HeuristicPlugin.__init__` 中的属性名与 Skeleton 框架中引用的属性名不一致，导致运行时抛出 `AttributeError`。

**根因分析**: LLM 根据上下文自行推断属性名，可能生成 `self.vehicle_cap` 而框架期望 `self.capacity`；或生成 `self.distance` 而框架期望 `self.dist_matrix`。每次生成的命名都不可控。

**解决方案**: 在 `generate_or_code_solver()` 中实施"统一 `__init__` 注入"策略：
```python
# 无论 LLM 是否生成了 __init__，一律替换为框架统一版本
unified_init = (
    "    def __init__(self, *args, **kwargs):\n"
    "        _data = kwargs.get('data', {})\n"
    "        self.capacity = _data.get('vehicle_capacity', 200)\n"
    "        self.customers = _data.get('customers', [])\n"
    "        self.dist_matrix = None   # 由 Solver 注入\n"
    "        self.solver = None        # 由 Solver 注入\n"
    "        self.customer_lookup = {c['id']: c for c in self.customers}\n"
)
```
同时在代码提取阶段，自动跳过 LLM 生成的 `__init__` 方法体，仅保留其他算子方法。

**影响范围**: `llm_heuristic.py` 代码提取逻辑

---

#### P2: LLM 生成多余算子 (`worst_removal` 干扰)

**现象**: 提示词中曾包含"不需要实现 `worst_removal`"的负面约束。然而 LLM（特别是推理型模型 DeepSeek R1）反而将 `worst_removal` 理解为需要实现的算子，生成了 6 个方法而非要求的 5 个，导致算子列表与框架不匹配。

**根因分析**: 大语言模型对否定指令的遵循能力有限，类似于经典的"不要想粉色大象"效应。在提示词中提及一个不应实现的名称，反而增加了该名称在 LLM 注意力中的权重。

**解决方案**: 彻底移除提示词中所有关于 `worst_removal` 的提及，采用纯正面引导策略：
```
你的类必须恰好包含以下5个方法（不多不少）：
  1. random_removal(self, solution, ratio)
  2. route_removal(self, solution, ratio)
  3. string_removal(self, solution, ratio)
  4. greedy_insert(self, solution, removed_nodes)
  5. regret_insert(self, solution, removed_nodes)
```
仅列出需要的方法名，不提及任何不需要的方法。

**设计原则**: **正面引导优于负面约束**——对 LLM 的指令应始终表述为"做什么"而非"不做什么"

**影响范围**: `heuristic_prompts.py` 全文, `llm_heuristic.py` 错误反馈消息

---

#### P3: 简化距离计算导致成本严重偏差

**现象**: LLM 在 `greedy_insert` 和 `regret_insert` 中使用简化的距离三角不等式计算插入成本：
```python
# LLM 生成的简化版本（错误）
cost_increase = dist[prev][node] + dist[node][next] - dist[prev][next]
```
而非调用完整的成本计算函数 `self.solver.calculator.calculate_route_cost()`。这导致插入决策仅考虑距离，完全忽略了新鲜度衰减（C₂）和时间窗惩罚（C₃），使得最终解的成本显著偏离真实目标函数。

**根因分析**: 简化距离计算是 VRP 文献中的常见模式，LLM 倾向于生成这种"教科书式"实现。在不加约束的情况下，LLM 默认使用最简单的评估方式。

**解决方案**: 在提示词模板中实施"三重强制"策略：
1. **模板开头**（第 2 层）: 加入醒目警告框，列出完整调用示例
2. **各算子说明中**: 在 `greedy_insert` 和 `regret_insert` 的指南中嵌入强制使用代码片段
3. **检查清单**（第 6 层）: 添加检查项 "✅ 修复算子使用 `calculate_route_cost()` 而非距离三角"

同时在 `generate_or_code_solver()` 中增加运行时检测：
```python
uses_full_cost = "self.solver.calculator.calculate_route_cost" in llm_plugin_code
uses_simple_dist = "self.dist_matrix[" in llm_plugin_code and "- self.dist_matrix[" in llm_plugin_code
if not uses_full_cost:
    print("⚠️ 警告：LLM生成的代码未使用完整成本计算函数！")
```

**影响范围**: `heuristic_prompts.py` 模板, `llm_heuristic.py` 代码验证

---

#### P4: LLM 生成代码执行失败（超时 / 缺方法 / 语法错误）

**现象**: LLM 生成的代码存在多种运行时问题：
- **执行超时**: `regret_insert` 中嵌套循环复杂度过高（$O(n^3)$），在 100 客户规模下单次迭代耗时超过限制
- **缺失方法**: LLM 有时只生成 3-4 个方法，遗漏 `route_removal` 或 `string_removal`
- **语法错误**: 缩进不一致、括号不匹配、变量未定义等

**解决方案**: 多层防御机制：

| 防御层 | 机制 | 实现位置 |
|--------|------|----------|
| 第 1 层 | 600 秒执行超时，`Popen` + `process.kill()` | `utils.py` |
| 第 2 层 | 缺失方法自动补全（桩代码注入） | `llm_heuristic.py` |
| 第 3 层 | Fallback 备用算子（运行时异常捕获） | `heuristic_skeleton.py` |
| 第 4 层 | 多轮重试（最多 5 次），将错误信息反馈给 LLM 重新生成 | `llm_heuristic.py` |

自动补全示例（当 `route_removal` 缺失时）：
```python
if 'def route_removal' not in plugin_class_code:
    print("[Auto-Fix] 补全缺失的破坏算子: route_removal")
    plugin_class_code += '''
    def route_removal(self, solution, ratio):
        """路径移除：随机移除整条路径"""
        if not solution: return solution, []
        non_empty = [(i, [n for n in r if n != 0])
                     for i, r in enumerate(solution) if any(n != 0 for n in r)]
        if not non_empty: return solution, []
        idx, customers = random.choice(non_empty)
        new_sol = [r[:] for i, r in enumerate(solution) if i != idx]
        return new_sol, customers
    '''
```

**影响范围**: `utils.py` 超时控制, `llm_heuristic.py` 自动补全, `heuristic_skeleton.py` Fallback

### 8.4 B 类问题: 算法参数与机制

#### P5: 随机种子导致多次运行结果完全相同

**现象**: 执行 `solve_multi_run(num_runs=3)` 时，3 次运行返回完全相同的最优成本和路径方案，多次运行失去意义。

**根因分析**: 早期代码中在 `solve()` 入口处设置了固定随机种子 `random.seed(42)`，导致每次运行的随机序列完全相同——相同的初始解排序、相同的算子选择、相同的 SA 接受决策。

**解决方案**: 移除所有 `random.seed()` 调用，让每次运行使用系统默认的随机状态（基于时间戳），确保运行独立性。

**影响范围**: `heuristic_skeleton.py` 中 `solve()` 方法

#### P6: 迭代次数不足，收敛不充分

**现象**: 初始配置 `max_iters=600`，收敛曲线显示在第 500-600 轮仍有下降趋势，算法被迫停止。

**优化过程**:
| 版本 | 迭代次数 | 观察 |
|------|----------|------|
| V0 | 600 | 曲线未收敛 |
| V1 | 800 | 收敛但仍有空间 |
| V2 | 1000 | 约 900 轮充分收敛 |

**权衡**: 1000 次迭代在 600 秒超时内可完成（实际耗时约 200-300 秒），时间预算充裕。

**影响范围**: `llm_heuristic.py` 中 `solver.solve(max_iters=...)` 调用

#### P8: 多次运行（`solve_multi_run`）冗余

**现象**: `solve_multi_run(max_iters=800, num_runs=3)` 总计 2400 次迭代，耗时长，但 3 次运行的最优成本差异小于 2%。

**结构性分析**: 单次 `solve()` 已内置三重随机化机制：

| 机制 | 作用 | 位置 |
|------|------|------|
| 3 个初始解策略 | 起始点多样性 | `solve()` 开头 |
| 模拟退火接受 | 过程中逃离局部最优 | `solve()` 主循环 |
| 重启 + 再加热 | 长期无改善时大扰动 | `solve()` 重启分支 |

**结论**: 单次 `solve()` 的搜索能力已覆盖多次运行的效果，`solve_multi_run` 的边际收益极低。

**解决方案**: 
- 调用方式：`solver.solve_multi_run(max_iters=800, num_runs=3)` → `solver.solve(max_iters=1000)`
- 节省算力（2400→1000 次迭代）同时提升单次质量（800→1000）

**影响范围**: `llm_heuristic.py` 中主执行代码

---

#### P12: 算子饥饿（Operator Starvation）

**现象**: 第一次优化后的运行结果显示严重的算子使用不均衡：

| 算子 | 使用次数 | 占比 | 状态 |
|------|----------|------|------|
| `random_removal` | ~500 | 50% | 正常 |
| `string_removal` | ~266 | 27% | 正常 |
| `route_removal` | **~32** | **3.2%** | ⚠ 饥饿 |

**根因分析**: ALNS 权重更新公式 $w \leftarrow (1-\rho) \cdot w + \rho \cdot \sigma$ 存在正反馈陷阱：
1. `route_removal` 初期表现较差（因路径级破坏在早期破坏力过大）→ 得分低
2. 权重降低 → 被选中概率降低 → 更少的使用机会
3. 更少的使用 → 更少的改善机会 → 权重进一步降低
4. 最终 $w \to 0$，算子完全被"饿死"

数学上，当连续 $n$ 轮获得 $\sigma=0$ 时：
$$w^{(n)} = (1-\rho)^n \cdot w^{(0)} = 0.9^n \cdot w^{(0)}$$
当 $n=50$ 时，$w^{(50)} = 0.9^{50} \approx 0.005$，权重已接近零。

**解决方案**: 引入权重下限保护（Weight Floor）：
```python
min_weight = 0.1
self.d_weights = [max(w, min_weight) for w in self.d_weights]
self.i_weights = [max(w, min_weight) for w in self.i_weights]
```
确保每个算子至少保留 $w_{min}/(w_{min} \times |\mathcal{O}|) = 1/|\mathcal{O}|$ 的最低选择概率（对 3 个破坏算子约 10%）。

**效果**: `route_removal` 使用量从约 32 次翻倍至约 60 次，搜索多样性显著提升。

**影响范围**: `heuristic_skeleton.py` 中 `update_weights()` 方法

if max_iters > 0 and current_run > 0 and in_iter_phase and iter_match:

current_run = 1   # 默认视为第1轮（单次运行）
total_runs = 1

#### P10: 图表 (c) 显示空白（"No multi-run data"）

**现象**: 将单次运行替代多次运行后，原图表 (c) 为"多次运行成本对比"柱状图，需要提取 `"第 1/3 次运行"` 等多轮数据。单次运行时无此数据，图表区域显示空白文字。

**解决方案**: 将图表 (c) 的功能从"多次运行对比"重新设计为"算子性能分析"：

| 对比维度 | 旧设计 (Multi-run Comparison) | 新设计 (Operator Performance) |
|----------|-------------------------------|-------------------------------|
| 数据来源 | 多次运行的成本列表 | 算子统计（使用次数、成功率） |
| 图表类型 | 单一柱状图 | 双 Y 轴（柱状图 + 折线图） |
| 信息密度 | 低（仅成本对比） | 高（5 个算子 × 3 维度） |
| 适用场景 | 仅多次运行 | 单次/多次均可 |

新图表包含：蓝色柱（破坏算子使用次数）、红色柱（修复算子使用次数）、橙色折线（成功率 %）

**影响范围**: `llm_heuristic.py` 中 `visualize_results()` 图表 (c) 部分

#### P11: 算子统计数据未输出，无法提取

**现象**: 框架内部 `self.op_stats` 字典记录了所有算子的使用次数和成功次数，但 `solve()` 方法结束时未将此数据打印到 `stdout`，外部的 `extract_operator_stats()` 正则无法匹配任何内容。

**解决方案**: 在 `solve()` 方法末尾（`return` 之前）添加统计打印代码：
```python
# 打印算子统计（供可视化提取）
destroy_names = ['random_removal', 'route_removal', 'string_removal']
insert_names = ['greedy_insert', 'regret_insert']
print("【算子统计】")
for idx, name in enumerate(destroy_names):
    s = self.op_stats['destroy'][idx]
    rate = (s['successes'] / s['uses'] * 100) if s['uses'] > 0 else 0.0
    print(f"  {name}: {s['uses']} uses, {s['successes']} success ({rate:.1f}%)")
```
输出格式经过设计，与 `extract_operator_stats()` 中的正则模式完全匹配：
```
  random_removal: 632 uses, 304 success (48.1%)
```

**影响范围**: `heuristic_skeleton.py` 中 `solve()` 方法末尾

---

#### P13: 算子性能图 (c) 标注文字重叠

**现象**: 图表 (c) 中同时存在两类标注——柱顶的使用次数和折线的成功率百分比。当某算子（如 `route_removal`）使用次数很低（柱子矮）而成功率点恰好在柱顶附近时，两个标注在视觉上完全重叠，无法辨读。

**解决方案**: 实施双维度动态定位策略：

**策略 1 — 柱顶标注防重叠**:
```python
if use_count < max_use * 0.15:
    # 低柱子：标注向上偏移，使用加粗字体增强可读性
    ax3.text(x, y + max_use * 0.02, f'{use_count}',
             ha='center', va='bottom', fontsize=8, fontweight='bold')
```

**策略 2 — 成功率标注自适应翻转**:
```python
# 计算柱顶与成功率点的归一化距离
bar_top_ratio = uses[xi] / max_use
rate_ratio = rate / max_rate / 1.5
if abs(bar_top_ratio - rate_ratio) < 0.15:
    # 距离过近 → 标注翻转到下方
    xytext = (0, -15); va = 'top'
else:
    xytext = (0, 8); va = 'bottom'
```

**影响范围**: `llm_heuristic.py` 中 `visualize_results()` 图表 (c) 标注部分

### 8.6 D 类问题: 工程与维护

#### P15: Notebook 与源文件的 858 行代码重复

**现象**: `test.ipynb` 中存在一个巨大的代码单元格（858 行），完整拷贝了 `llm_heuristic.py` 的全部内容（包括 API Key、函数定义、可视化代码等）。当修改主文件时，必须同步修改 Notebook，否则两处代码行为不一致。

**问题影响**:
- **维护成本**: 每次修改需要编辑两个文件
- **一致性风险**: 多次出现 Notebook 仍使用旧版 `solve_multi_run` 而主文件已改为 `solve` 的情况
- **版本控制**: `.ipynb` 是 JSON 格式，大量内联代码导致 diff 难以阅读

**解决方案**: 将 Notebook 重构为 import 方式，从 858 行缩减至约 85 行：
```python
import sys, os
sys.path.append(os.path.dirname(os.path.abspath('.')))
from llm_heuristic import (
    generate_or_code_solver, visualize_results,
    extract_solution_from_output, load_solomon_data, print_header
)
# ... 调用函数，无需重复定义
```

**设计原则**: **Single Source of Truth** — 算法逻辑只在 `llm_heuristic.py` 中定义一次

**影响范围**: `test.ipynb` 全部代码单元格

#### P16: 文件编辑失败（引号转义与 JSON 编码）

**现象**: 在开发过程中，使用文本替换工具编辑 `.py` 和 `.ipynb` 文件时多次失败：
1. **Python 文件**: 搜索文本中的单引号 `'` 与源文件中的转义引号 `\'` 不匹配
2. **Notebook 文件**: `.ipynb` 是 JSON 格式，字符串中的特殊字符（换行、引号）经过 JSON 编码，直接搜索 Python 源码文本无法匹配

**具体案例**:
- 替换图表 (c) 标题时，源文件中 `title='(c) Multi-run Comparison'` 的引号在编辑工具中被解析为不同的引号类型，导致精确匹配失败
- 在 Notebook 中修改 `solve_multi_run` 调用时，JSON 编码后的 `\n` 和 `\"` 使得文本替换无法定位

**解决方案**: 
1. 对 `.py` 文件：使用更多上下文行（3-5 行）确保唯一匹配
2. 对 `.ipynb` 文件：使用 Notebook 专用编辑 API 而非通用文本替换
3. 多次失败时：直接替换整个代码单元格内容

**经验教训**: Notebook 文件的编辑应始终使用结构化 API，避免对 JSON 内部进行文本级操作

**影响范围**: 开发工具链（非代码层面）

## 9. 实验结果与分析

### 9.1 实验配置

| 项目     | 配置                                   |
| -------- | -------------------------------------- |
| 基准实例 | Solomon C105, 100 个客户, 车辆容量 200 |
| LLM 模型 | DeepSeek R1 (火山引擎 Endpoint)        |
| 迭代次数 | 1000                                   |
| 执行超时 | 600 秒                                 |
| 最大尝试 | 5 次（LLM 代码生成）                   |

### 9.2 最终结果

| 指标         | 值                        |
| ------------ | ------------------------- |
| **最优成本** | **42,023.80**             |
| 路径数量     | 34                        |
| 总迭代次数   | 1000                      |
| 最后改进迭代 | ~900                      |
| 可行性       | ✓ (通过容量 + 时间窗验证) |

### 9.3 优化对比

| 版本        | 迭代 | 运行方式 | 最优成本      | 改进幅度            |
| ----------- | ---- | -------- | ------------- | ------------------- |
| V1 (初始)   | 800  | 3次运行  | 42,775.07     | —                   |
| V2 (优化后) | 1000 | 单次运行 | **42,023.80** | **−751.27 (−1.8%)** |

### 9.4 算子统计分析

最终运行的算子使用情况：

| 算子             | 类型 | 使用次数 | 成功次数 | 成功率 |
| ---------------- | ---- | -------- | -------- | ------ |
| `random_removal` | 破坏 | ~632     | ~304     | 48.1%  |
| `route_removal`  | 破坏 | ~60      | ~5       | ~8.3%  |
| `string_removal` | 破坏 | ~317     | ~86      | 27.1%  |
| `greedy_insert`  | 修复 | ~237     | ~73      | 30.8%  |
| `regret_insert`  | 修复 | ~763     | ~322     | 42.2%  |

**分析**:

1. **`random_removal` 主导破坏**: 约 63% 的破坏操作由随机移除完成，成功率最高（48.1%），说明在此问题规模下随机扰动的探索效率很高
2. **`regret_insert` 优于 `greedy_insert`**: 后悔插入的使用量（~763 次）远高于贪心插入（~237 次），且成功率更高（42.2% vs 30.8%），符合文献中后悔插入在时间窗约束问题中的优势
3. **`route_removal` 使用量低但有价值**: 虽然仅约 60 次使用，但权重下限保护机制确保了搜索多样性，避免陷入单一搜索模式
4. **收敛持续至 ~900 轮**: 从 800 次扩展到 1000 次迭代后，算法在约 900 轮仍找到了改进，证明了增加迭代预算的价值

### 9.5 收敛行为

从收敛曲线 (a) 可以观察到：

- **快速下降期** (0-200 轮): 初始解快速改进，成本大幅下降
- **波动探索期** (200-600 轮): SA 温度较高，当前成本呈现显著波动（灰色曲线），但最优成本稳步下降
- **精细优化期** (600-900 轮): 温度降低，波动减小，间歇性发现更优解
- **收敛稳定期** (900-1000 轮): 算法基本收敛，成本趋于稳定

这一行为模式体现了 SA 接受准则在探索（Exploration）与利用（Exploitation）之间的平衡。

## 10. 结论与展望

### 10.1 主要结论

1. **LLM 可有效生成 ALNS 算子**: DeepSeek R1 在提示工程引导下，能够生成功能正确的破坏和修复算子代码，在 Solomon C105 基准上取得 42,023.80 的目标函数值
2. **插件式架构保证鲁棒性**: Skeleton + Plugin 的解耦设计，配合 Fallback 机制，即使 LLM 生成的部分算子存在缺陷，系统仍能正常运行
3. **自适应机制的重要性**: 权重下限保护、自适应破坏比例、重启再加热等机制显著影响算法性能，防止过早收敛和算子饥饿
4. **单次运行即可**: 内置的三重随机化机制使单次 `solve()` 已具备足够的搜索能力，多次运行的边际收益极低

### 10.2 局限性

1. **问题规模**: 当前仅在 100 客户规模上测试，更大规模实例（500+客户）的性能有待验证
2. **LLM 依赖**: 算子质量取决于 LLM 的代码生成能力，不同 LLM 可能产生差异较大的结果
3. **成本函数固定**: 当前成本模型为硬编码，扩展到其他 VRP 变体（如多仓库、异构车队）需要重新设计
4. **缺少对比基线**: 未与传统手工实现的 ALNS 或其他元启发式算法进行系统对比

### 10.3 未来工作

1. **多 LLM 对比**: 在相同提示下对比 GPT-4o、Claude、Gemini 等模型生成算子的质量
2. **自适应提示**: 根据首轮执行结果自动调整提示词，形成"提示-执行-反馈"闭环
3. **大规模测试**: 在 Solomon R 类和 RC 类实例，以及 Gehring & Homberger 大规模实例上验证
4. **算子进化**: 多轮对话中让 LLM 根据算子统计数据改进低效算子的实现
